# 2026-11-12 · 批量组加载（#6）决策：暂不做

> 状态：**已决定，暂不实现**。数据截至 2026-11-12。
> 相关提议：给 `search_tools` 增加 `groups: [...]`，一次调用加载多个组（交接 #6）。

## 决策

不做。不启动该功能，`search_tools` 保持一次一个 `query` 的形态。

## 证据

对 `benchmark/results/` 的 130 个真实会话做只读分析（其中 109 个调用过 `search_tools`，均为 native 执行）：

| 指标 | 结果 |
|---|---|
| 至少整组加载一次 | 24 会话（22.0%） |
| 整组加载 / 普通加载调用 | 26 / 109 |
| 加载 ≥2 个不同组 | 2 会话（1.8%） |
| 批量 API 可省调用（全样本上限） | 2 次 |
| 生产 arm（`agent-auto` + `agent-catalog`）多组会话 | 0 / 27 |
| 同组重复加载 | 0 |
| 被 `groupMaxResults` 截断的整组加载 | 0 |
| 样本中的 PTC（`run_code`）会话 | 0 / 130 |

关键细节：两个多组会话都在同一个 assistant step 内并行发出两次 `search_tools`（相隔 6–9 ms），
批量 API 只会把两次调用合成一次，**省不到模型轮次**。

## 为什么不现在做

- 批量组加载的收益场景是“模型预先知道要 2+ 个组，且调用分散在不同 step”；观测到的多组调用已经并行，没有这个模式。
- PTC 下多次 `search_tools` 可以写在同一个 `run_code` 程序里，同样省不到模型轮次，收益只会更弱。
- 新特性要改参数 schema、返回文案、限额语义和测试，属于 0.4.0 级别；没有需求证据时引入，违背“净增量为前提”。

## 何时重新评估

- 遥测/会话记录出现跨 step 的多组加载，或同组重复加载；
- 出现需要一次性加载多个组的具体工作流；
- 届时作为独立特性设计（`groups: [...]`），明确每组/总上限、部分组不存在时的返回、顺序与去重，
  并单独加测试；不混进文案补丁。

## 数据局限

benchmark 任务偏单领域，且样本全为 native，可能低估多组需求；结论是“现在没有证据支持”，不是“永远不做”。
