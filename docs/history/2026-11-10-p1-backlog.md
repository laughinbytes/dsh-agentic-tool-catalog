## P1-1（待决）首次启动 bootstrap 扁平目录是否足够好

**现状**：真·首次（无内存/磁盘缓存、无 lastKnownGood）时给模型 bootstrap 扁平工具名单（前 20 个名字 + 总数），
`search_tools` 仍可按名字/描述搜索；后台生成约 **73s**（实测）后自动切换为 agent 分组。
目录变化时已改为立即沿用 last-known-good（不再掉回 bootstrap）；重启有磁盘缓存（待真实重启验证）。

**问题**：首分钟没有分组、没有整组加载；模型在 30–50+ 工具后选择准确率会下降；若首次生成失败且无历史，
会停留在 bootstrap（有显式告警 + 10 分钟退避）。

**候选方案（待定）**：
| 方案 | 优点 | 代价 |
|---|---|---|
| 保持现状（bootstrap 过渡） | 不阻塞、不丢工具、不造假分组 | 首分钟质量弱 |
| 阻塞等首次生成 | 首请求质量最高 | 首请求 +60–90s |
| 安装/加载时预热 | 首次会话前大概率完成 | 需可靠触发时机；成本提前；需防重复 |
| 打包 seed 目录 | 即时高质量 | 只适用于特定 profile，不通用 |
| 轻量启发式引导分组 | 即时、质量中上 | 违背"删除旧策略"的决定，不做 |

**建议**（等拍板）：保持 bootstrap 但做三件事——① 更早预热（插件加载即开始，尽量让第一个用户会话前完成）；
② 提示文案明确"目录初始化中，约 1 分钟自动分组"；③ 失败可见可恢复（告警 + 自动退避重试 + `agentGroupResetNonce` 手动强制）。
另把"冷启动窗口"和"磁盘缓存命中率"作为发布 benchmark 的独立指标。

## P1-2 增量重生成

目录小变化时只让子代理处理"新增/消失"的工具，保留已有组 id，目标把一次生成从 ~71s 降到几秒，
并减少组名漂移。实现要点：把上次分组 + 差异工具列表作为输入；输出只允许新增组/迁移少量工具；校验不变。

### 实施状态（2026-11-10 晚）

- ✅ 代码已实现：目录变化时把"上次成功分组 + 新增工具清单"交给子代理做**最小改动**（保留组 id/描述/成员，必要时才拆合），首轮增量失败自动退回全量；新增统计 `incrementalRuns`。
- ✅ **已真实实测（2026-11-10 23:1x）**：临时 nonce 强制缓存 miss → 恢复会话首条消息触发懒生成；
  使用增量模式一次通过（`incrementalRuns=1`、`runs 1→2`、`failures=0`），**18 个组 id/结构全部保留**（browser-input 等不变），
  本次"无实际新增工具"的极端情况下耗时约 65s（与全量相当；真实增量应更快，主要收益是 id 稳定 + prompt 更小）。

## P1-7（已发现并部分修复）启动期工具表抖动

**现象（2026-11-10 真实重启验证实测）**：App 启动时 MCP 工具是陆续出现的（先 66 个、后 70 个）。
插件在 66 个时启动生成；目录增长到 70 后，这次结果因指纹过期被丢弃，但**没有为最新指纹重新触发**，
agent 会卡在 adapted/bootstrap 目录直到下次 tools/change。

**已修**：生成结束若发现目录已变（`enrichment.dirty`），立即为最新指纹重新走一轮（通常直接命中磁盘缓存）。

**待优化（P1）**：① 启动时对 `tools/change` 做 1–2 秒 debounce，等工具表稳定后再发起生成，避免为半成品目录白跑一次；
② 缓存命中时把 `lastGood` 对齐到当前指纹（当前 lastGood 可能被半成品目录覆盖）；
③ 把该场景加入重启 benchmark 断言（runs 不应为半成品目录增长）。
